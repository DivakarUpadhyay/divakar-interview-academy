# Overview

**SSIS (SQL Server Integration Services)** is Microsoft's ETL and workflow platform, part of SQL Server. You build **packages** (`.dtsx` XML files) visually in Visual Studio, then deploy them to the **SSIS Catalog (SSISDB)** and run them with SQL Server Agent.

A package has two main designers:

- **Control Flow** — the workflow: tasks (Execute SQL, Data Flow, File System, Script, Send Mail...) connected by **precedence constraints**, grouped in **containers** (Sequence, For Loop, Foreach Loop).
- **Data Flow** — the row pipeline inside a Data Flow Task: **sources → transformations → destinations**, processed in memory buffers.

Typical uses: loading data warehouses, migrating data, importing/exporting files, cleansing data, automating database maintenance.

# Lifecycle

**Package development lifecycle:** requirements → design (source-to-target mapping) → develop in Visual Studio (SSIS project) → debug with data viewers/breakpoints → configure parameters → build (`.ispac`) → deploy to SSISDB (dev → test → prod) → configure **environments** per server → schedule with SQL Agent → monitor via SSISDB reports → maintain.

**Package execution lifecycle:**

1. Package loads; **validation** of tasks and connections (can be delayed with `DelayValidation=True`).
2. **Parameters/variables** are set (from environment references, `/SET` options, or expressions).
3. **OnPreExecute** events fire; Control Flow executes tasks in order determined by **precedence constraints** (Success/Failure/Completion, optionally with expressions).
4. For each **Data Flow Task**: the pipeline engine allocates buffers, sources read rows, transformations process buffers, destinations write; error outputs redirect bad rows.
5. **Event handlers** (OnError, OnWarning, OnPostExecute, OnTaskFailed...) run when events bubble up.
6. **Logging** writes to SSISDB catalog views (or log providers).
7. **Checkpoints** (if enabled) record completed tasks so a restart resumes after the failure point.
8. Package completes with Success/Failure result.

**Data flow buffer lifecycle:** source fills a buffer (default `DefaultBufferMaxRows` 10,000 rows / `DefaultBufferSize` 10 MB) → **synchronous** transformations modify the same buffer in place → **asynchronous** transformations copy rows into new buffers → destination writes the buffer → buffer reused.

# Module: Package Basics

## Lesson: [Basic|High] Package anatomy: control flow vs data flow

| Control Flow | Data Flow |
|---|---|
| **Workflow** of tasks | **Row-by-row pipeline** inside one Data Flow Task |
| Elements: tasks, containers, precedence constraints | Elements: sources, transformations, destinations, paths |
| Runs tasks one after another (or in parallel) | Streams data through memory buffers |
| Handles files, SQL commands, emails, loops | Extracts, transforms, loads rows |

Common **Control Flow tasks**: Execute SQL Task, Data Flow Task, Execute Package Task, File System Task, FTP Task, Script Task (C#), Send Mail Task, Expression Task, Bulk Insert Task, Execute Process Task, Web Service Task, XML Task, CDC Control Task, Analysis Services Processing Task, maintenance plan tasks.

**Containers**: Sequence (group tasks, scope variables, shared transactions), For Loop (counter-based), Foreach Loop (enumerators: File, ADO recordset, Item, Variable, SMO, Azure Blob...), and the implicit Task Host around each task.

## Lesson: [Basic|High] Connection managers

Connection managers define how to connect; tasks and components reference them.

- **OLE DB** (SQL Server via Microsoft OLE DB Driver for SQL Server — MSOLEDBSQL), **ADO.NET**, **ODBC**
- **Flat File** (CSV, fixed width), **Excel**, **Multiple Flat Files**, **Raw File**
- **FTP**, **HTTP**, **SMTP**, **File**, **Cache** (for lookups), **Azure Storage / Data Lake** (Azure Feature Pack)

Project-level connection managers are shared by all packages in the project. Make connection strings configurable with **parameters + expressions** so the same package runs in dev/test/prod.

## Lesson: [Basic|High] Variables, parameters and expressions

| | Variables | Parameters (2012+) |
|---|---|---|
| Scope | Package, container or task | Package or project |
| Change at runtime | Yes, by tasks/scripts | Read-only during execution; set before execution |
| Use | Store values between tasks (row counts, file names, result sets) | Pass external values in (server names, folders, dates) |
| Set from | Execute SQL results, Script Task, expressions | SSISDB environments, `dtexec /Par`, Agent job |

**Expressions** (SSIS expression language, C-like) make properties dynamic:

```
@[User::FilePath] + "\\Sales_" + (DT_WSTR, 8) (YEAR(GETDATE()) * 10000 + MONTH(GETDATE()) * 100 + DAY(GETDATE())) + ".csv"
"SELECT * FROM dbo.Orders WHERE ModifiedAt > '" + (DT_WSTR, 30) @[User::LastLoad] + "'"
@[$Project::ServerName]          -- project parameter
ISNULL(Discount) ? 0 : Discount   -- in Derived Column
```

System variables: `System::PackageName`, `System::StartTime`, `System::ExecutionInstanceGUID`, `System::ErrorDescription` (in event handlers).

## Lesson: [Basic|Medium] Precedence constraints

Arrows between tasks that decide what runs next:

- **Success** (green), **Failure** (red), **Completion** (blue — either way).
- **Expression** or **Expression and Constraint** — e.g. run only if `@[User::RowCount] > 0`.
- Multiple incoming constraints: **Logical AND** (all must be satisfied — default) or **Logical OR** (any one).

# Module: Data Flow

## Lesson: [Basic|High] Sources and destinations

- **Sources**: OLE DB Source (table, SQL command, SQL command from variable), ADO.NET Source, Flat File Source, Excel Source, XML Source, Raw File Source, ODBC Source, CDC Source.
- **Destinations**: OLE DB Destination (**Table or view – fast load** uses bulk insert: set Rows per batch, Maximum insert commit size, Table lock, Check constraints), SQL Server Destination (local server only), Flat File, Excel, Raw File, ADO.NET, ODBC, Recordset Destination (to an object variable).

Prefer a **SQL command** in sources that selects only needed columns and filters/sorts on the server, rather than "Table or view".

## Lesson: [Intermediate|High] Transformations and their types

| Transformation | Purpose | Blocking type |
|---|---|---|
| Derived Column | New/replace column via expression | Non-blocking (synchronous) |
| Data Conversion | Convert data types (e.g. DT_STR → DT_WSTR) | Non-blocking |
| Conditional Split | Route rows by conditions (like CASE) | Non-blocking |
| Multicast | Send all rows to many outputs | Non-blocking |
| Lookup | Match against reference data | Non-blocking (synchronous) |
| Row Count | Count rows into a variable | Non-blocking |
| Copy Column, Character Map, Audit | Simple row operations | Non-blocking |
| OLE DB Command | Run SQL **per row** (slow!) | Non-blocking but row-by-row |
| Script Component | Custom C# (source, transformation or destination) | Depends |
| Merge, Merge Join, Union All | Combine inputs (Merge/Merge Join need sorted input) | Semi-blocking |
| Pivot / Unpivot | Reshape columns/rows | Semi-blocking |
| **Sort** | Sort rows (optionally remove duplicates) | **Fully blocking** |
| **Aggregate** | GROUP BY, SUM, COUNT... | **Fully blocking** |
| Fuzzy Lookup / Fuzzy Grouping | Approximate matching, dedup | Fully blocking |
| Slowly Changing Dimension | SCD wizard (types 0, 1, 2) | Row-by-row |
| Percentage/Row Sampling, Term Extraction | Sampling/text mining | Varies |

**Synchronous** (non-blocking): output rows = input rows, same buffer, fastest. **Asynchronous**: new buffers; **semi-blocking** passes some rows before all input is read; **fully blocking** must read **all** input before output (Sort, Aggregate) → memory heavy.

## Lesson: [Intermediate|High] Lookup transformation and cache modes

Lookup matches each input row against a reference dataset (e.g. get `CustomerKey` from `DimCustomer` by `CustomerId`).

| Cache mode | How | When |
|---|---|---|
| **Full cache** (default) | Loads the entire reference query into memory before rows flow | Reference fits in memory — fastest |
| **Partial cache** | Queries DB on cache miss, caches results | Large reference, few distinct keys used |
| **No cache** | Queries DB for every row | Reference changes during the load; tiny inputs |
| **Cache Connection Manager** | Cache built once (Cache Transform), reused by several lookups/packages | Same reference used many times |

Outputs: **Match**, **No Match** (configure "Redirect rows to no match output" — e.g. to insert new dimension members), **Error**. Lookups are **case-sensitive** and type-sensitive in full cache mode — trim/upper both sides. Use a SQL query selecting only key + needed columns.

## Lesson: [Intermediate|High] Implementing incremental loads and SCD in SSIS

**Pattern 1: Lookup-based upsert**

```
OLE DB Source (changed rows since watermark)
  → Lookup on target by business key
      ├─ No Match → OLE DB Destination (fast load INSERT)
      └─ Match    → Conditional Split (columns changed?) → OLE DB Destination to a staging "updates" table
Execute SQL Task after the data flow: UPDATE target FROM staging updates (set-based)
```

**Pattern 2: Load staging, then MERGE** — Data Flow loads staging; an Execute SQL Task runs a T-SQL `MERGE` or SCD2 statements. Usually the fastest and simplest for large volumes.

**SCD wizard** — quick to configure (Fixed = Type 0, Changing = Type 1, Historical = Type 2, inferred members) but uses OLE DB Command per row → slow on big dimensions; replace with set-based SQL in production.

**Watermark** — Execute SQL Task reads `LastLoaded` into a variable → source query uses it → final Execute SQL updates it on success. Or use **CDC Control Task + CDC Source + CDC Splitter** (2012+) with SQL Server CDC.

# Module: Error Handling, Logging and Restartability

## Lesson: [Intermediate|High] Error outputs, event handlers and logging

- **Data flow error outputs** per component: *Fail component* (default), *Ignore failure*, or *Redirect row* — send bad rows (conversion errors, truncation) to an error table with `ErrorCode` and `ErrorColumn` (use `GetErrorDescription` in a Script Component to get the text).
- **Event handlers** at package/container/task level: `OnError` (log error, send mail), `OnPreExecute`/`OnPostExecute` (audit timings), `OnTaskFailed`, `OnWarning`, `OnVariableValueChanged`. Use `System::Propagate = False` in a handler to stop an error bubbling up.
- **MaximumErrorCount** — how many errors before the container fails (default 1).
- **Logging**: in the project deployment model, SSISDB logs automatically at the chosen **logging level** (None, Basic — default, Performance, Verbose, RuntimeLineage, custom). Legacy log providers: SQL Server table (`sysssislog`), text file, Windows Event Log, XML.
- Built-in SSMS reports: "All Executions", "Execution Performance", per-message details; catalog views `catalog.executions`, `catalog.event_messages`, `catalog.execution_data_statistics`.

## Lesson: [Intermediate|Medium] Checkpoints and transactions

**Checkpoints** let a failed package restart from the failed task instead of the beginning:

- Package properties: `CheckpointFileName`, `CheckpointUsage = IfExists`, `SaveCheckpoints = True`.
- Each task to be a restart point: `FailPackageOnFailure = True`.
- Data flow tasks restart from the beginning of that data flow (not mid-flow) — design them to be idempotent (truncate staging first).
- Not supported well with Foreach Loops (the whole loop reruns) and don't combine checkpoints with transactions casually.

**Transactions**: `TransactionOption` property — `Required` (start or join), `Supported` (join if exists — default), `NotSupported`. SSIS transactions use **MSDTC** (distributed) which must be running and configured. Alternative: native SQL transactions with Execute SQL Tasks (`BEGIN TRAN`/`COMMIT`) on a connection manager with `RetainSameConnection = True`.

# Module: Deployment, Scheduling and Performance

## Lesson: [Intermediate|High] Project vs package deployment model and SSISDB

| | Package deployment (legacy) | **Project deployment** (2012+) |
|---|---|---|
| Unit | Individual `.dtsx` | Whole project `.ispac` |
| Stored | File system or msdb | **SSISDB catalog** |
| Configuration | Package configurations (XML, SQL table, env vars) | **Parameters + environments** |
| Logging | Log providers you configure | Automatic catalog logging + reports |
| Versioning | Manual | Catalog keeps project versions; rollback |

**SSISDB catalog workflow:**

1. Create the catalog (SSMS → Integration Services Catalogs → Create Catalog; needs CLR enabled and a password for the encryption key).
2. Create a **folder**, deploy the `.ispac` (Deployment Wizard, SSMS, `ISDeploymentWizard.exe`, Azure DevOps task).
3. Create **environments** (DEV/QA/PROD) with variables (server name, file paths; sensitive values encrypted).
4. Add an **environment reference** to the project and map parameters to environment variables.
5. Execute via SSMS, `catalog.create_execution` + `catalog.start_execution` stored procedures, or a SQL Agent job step (type *SQL Server Integration Services Package*, select environment).

```sql
DECLARE @exec_id BIGINT;
EXEC SSISDB.catalog.create_execution @folder_name = N'ETL', @project_name = N'SalesDW', @package_name = N'LoadFactSales.dtsx',
     @reference_id = 1, @execution_id = @exec_id OUTPUT;
EXEC SSISDB.catalog.set_execution_parameter_value @exec_id, @object_type = 50, @parameter_name = N'LOGGING_LEVEL', @parameter_value = 1;
EXEC SSISDB.catalog.start_execution @exec_id;
```

```bat
dtexec /ISServer "\SSISDB\ETL\SalesDW\LoadFactSales.dtsx" /Server "PRODSQL01" /Env 1 /Par "$Project::LoadDate";"2026-10-20"
```

## Lesson: [Intermediate|Medium] Script Task and Script Component

- **Script Task** (Control Flow) — C#/VB code for workflow logic: check if a file exists, call an API, move files, set variables (`Dts.Variables["User::FileName"].Value = ...`), set `Dts.TaskResult = (int)ScriptResults.Success`.
- **Script Component** (Data Flow) — as a **source** (generate rows from an API/JSON), **transformation** (`Input0_ProcessInputRow(Input0Buffer Row)` to modify rows — e.g. complex regex cleansing), or **destination**.
- Declare `ReadOnlyVariables`/`ReadWriteVariables` in the editor before using them.

```csharp
public override void Input0_ProcessInputRow(Input0Buffer Row)
{
    Row.PhoneClean = Regex.Replace(Row.Phone ?? "", @"[^\d]", "");
    if (Row.PhoneClean.Length != 10) Row.IsValid = false;
}
```

## Lesson: [Advanced|High] Performance tuning

1. **Source**: SQL command with only needed columns, filters and `ORDER BY` on the server (set `IsSorted`/`SortKeyPosition` on the source output instead of a Sort transformation); use `NOLOCK` only if dirty reads are acceptable.
2. **Avoid blocking transformations** (Sort, Aggregate, Fuzzy) on big data — push to SQL.
3. **Replace OLE DB Command** (row-by-row) with staging + set-based UPDATE/MERGE.
4. **Lookups**: full cache with minimal columns; Cache Connection Manager for reuse.
5. **Destination fast load**: Table lock, sensible `Rows per batch` and `Maximum insert commit size`, disable/drop non-clustered indexes during large loads and rebuild after; check constraints off when safe.
6. **Buffers**: tune `DefaultBufferMaxRows`/`DefaultBufferSize` (or `AutoAdjustBufferSize=True` 2016+); narrow data types reduce row width = more rows per buffer.
7. **Parallelism**: `MaxConcurrentExecutables` (package) and `EngineThreads` (data flow); split independent loads into parallel tasks/packages.
8. **Avoid unnecessary data conversion**; match types to destination early.
9. **Run SSIS on/near the SQL Server** to reduce network hops; ensure enough memory (buffer spooling to disk = slow — watch "Buffers spooled" counter).
10. **Incremental loads** instead of full reloads.

# Interview

## [Beginner|High] What is SSIS and what is it used for?

SQL Server Integration Services is Microsoft's ETL and workflow tool shipped with SQL Server. It extracts data from many sources (SQL, Oracle, flat files, Excel, XML, APIs), transforms it in a high-performance in-memory pipeline, and loads it into targets such as data warehouses. Also used for data migration, file automation and database maintenance. Packages are built in Visual Studio and deployed to the SSISDB catalog.

## [Beginner|High] What is the difference between Control Flow and Data Flow?

Control Flow orchestrates the workflow: tasks (Execute SQL, Data Flow, File System, Script, Send Mail), containers and precedence constraints determining execution order. Data Flow is inside a Data Flow Task and moves rows from sources through transformations to destinations in memory buffers. Control Flow deals with tasks; Data Flow deals with rows.

## [Beginner|High] What are the different types of containers?

Sequence Container (groups tasks, scopes variables, shares transactions, lets you enable/disable a group), For Loop Container (repeats while a condition holds — counter-based), Foreach Loop Container (iterates over a collection: files in a folder, rows of an ADO recordset, items, nodes, blobs), and the Task Host container that wraps every single task.

## [Beginner|High] What is a precedence constraint?

A connector between control-flow executables that controls whether the next task runs, based on the outcome of the previous one: Success, Failure or Completion, optionally combined with an expression (e.g. only if `@RowCount > 0`). With multiple constraints into one task, choose logical AND (all) or OR (any).

## [Beginner|High] What is the difference between variables and parameters?

Parameters (introduced in 2012) pass values into a package or project from outside before execution — server names, folders, dates — and are set from SSISDB environments or `dtexec`. They are read-only during execution. Variables store values during execution (row counts, file names, result sets), can be changed by tasks/scripts, and are scoped to package, container or task.

## [Beginner|Medium] What is a connection manager?

A reusable object holding connection information (connection string, credentials) for a data source/destination — OLE DB, ADO.NET, Flat File, Excel, FTP, SMTP, Cache, Azure. Tasks and components reference it. Project-level connection managers are shared across packages. Make them dynamic with parameters/expressions for each environment.

## [Intermediate|High] What are synchronous and asynchronous transformations? Give examples of blocking transformations.

Synchronous (non-blocking) transformations process rows in the same buffer and output exactly one row per input row — Derived Column, Data Conversion, Conditional Split, Lookup, Multicast, Row Count. Asynchronous transformations create new buffers. Semi-blocking ones (Merge, Merge Join, Union All, Pivot) can output before reading all input; fully blocking ones (Sort, Aggregate, Fuzzy Grouping/Lookup) must read all input first, consuming memory and slowing large flows.

## [Intermediate|High] Explain the Lookup transformation cache modes.

Full cache loads the whole reference query into memory before processing (fastest, needs memory, reference must be stable). Partial cache starts empty and queries the database on misses, caching the results (good for large references with few used keys). No cache queries the database for every row (slowest; use when the reference changes during the load). A Cache Connection Manager can pre-build a cache from any source and reuse it across lookups/packages.

## [Intermediate|High] How do you handle errors in SSIS?

At row level, configure component error outputs to redirect failing rows (conversion/truncation/lookup no-match) to error tables with ErrorCode/ErrorColumn instead of failing. At task level, use precedence constraints on Failure to run cleanup/notification tasks, event handlers (OnError logs to an audit table and sends email), MaximumErrorCount, and checkpoints for restart. Logging in SSISDB captures messages; SQL Agent alerts on job failure.

## [Intermediate|High] How do you implement an incremental load in SSIS?

Store the last successful load watermark (date/rowversion) in a control table; Execute SQL Task reads it into a variable; the source query extracts rows changed since then; Lookup against the target splits new (No Match → insert) vs existing rows (Match → conditional split on changes → staging table → set-based UPDATE); final Execute SQL Task updates the watermark. Alternatives: CDC components, or load staging and run a T-SQL MERGE.

## [Intermediate|High] What is the difference between the project and package deployment models?

The package deployment model (legacy) deploys individual .dtsx files to the file system or msdb and uses package configurations. The project deployment model (2012+) deploys the whole project as an .ispac to the SSISDB catalog, uses project/package parameters with environments per server, keeps versions, and provides built-in logging and execution reports. New work should use the project model.

## [Intermediate|Medium] What are checkpoints in SSIS?

A restart mechanism: when enabled (CheckpointFileName, CheckpointUsage=IfExists, SaveCheckpoints=True, and FailPackageOnFailure=True on tasks), SSIS writes completed tasks to a checkpoint file; on rerun after failure it skips completed tasks and resumes from the failed one. Data flows restart from their beginning, so design them idempotently. The file is deleted after a successful run.

## [Intermediate|Medium] Merge vs Merge Join vs Union All?

Union All combines multiple inputs into one without requiring sorted input (like SQL UNION ALL) — preferred. Merge combines exactly two **sorted** inputs into one sorted output. Merge Join joins two **sorted** inputs (inner, left outer, full outer) on keys, like a SQL join. Both Merge and Merge Join need sorted inputs — sort in the source queries, not with Sort transformations.

## [Intermediate|Medium] How do you deploy and schedule SSIS packages?

Build the project to an .ispac; deploy to the SSISDB catalog with the Deployment Wizard, SSMS or a CI/CD pipeline (Azure DevOps SSIS deploy task); create environments with server-specific values and map parameters; schedule with a SQL Server Agent job step of type SSIS package referencing the catalog and environment; monitor through SSISDB reports and Agent job history. In Azure, run on an Azure-SSIS Integration Runtime triggered by Azure Data Factory.

## [Advanced|High] How do you improve the performance of a slow SSIS package?

Filter and select only needed columns at the source; sort in SQL and mark outputs as sorted; remove blocking transformations; replace OLE DB Command and SCD wizard with staging + set-based SQL; use full-cache lookups with minimal columns; fast-load destinations with table lock and batch settings; drop/disable indexes during huge loads; tune buffer size/rows (or AutoAdjustBufferSize); run independent flows in parallel (MaxConcurrentExecutables, EngineThreads); avoid unnecessary data conversions; check for buffer spooling and server memory; switch to incremental loads.

## [Advanced|Medium] What are the SSISDB logging levels?

None, **Basic** (default — errors, warnings, task start/finish), **Performance** (performance stats and errors/warnings, less detail), **Verbose** (all events including data flow component details — heavy), **RuntimeLineage** (lineage tracking data), plus custom levels (2016+) choosing specific events. Choose Basic for production; Verbose only for troubleshooting. Clean up old logs via the catalog retention settings (`Retention Period`).

## [Advanced|Medium] How do you run SSIS in the cloud?

Provision an **Azure-SSIS Integration Runtime** in Azure Data Factory (or Synapse) — a managed cluster of VMs that runs SSIS packages; host SSISDB in Azure SQL Database/Managed Instance or deploy packages to Azure Files; trigger with ADF's Execute SSIS Package activity. Use a self-hosted IR as proxy or VNet join to reach on-prem sources. Longer-term, migrate logic to native ADF/Fabric pipelines and dataflows.

## [Scenario|High] A package that loads 10 million rows nightly suddenly fails with a truncation error on one column. How do you handle it?

Identify the column from the error (ErrorColumn ID → lineage ID/name in the advanced editor or catalog messages). Short term: configure that component's error output to **redirect** truncated rows to an error table so the rest loads, and alert. Root cause: the source started sending longer values — confirm with data profiling, then widen the staging/target column and the SSIS metadata (refresh external columns), or apply a business rule (trim/substring) agreed with the business. Add a data-quality check that reports length violations.

## [Scenario|High] You need to process every CSV file that lands in a folder, archive successfully processed files and move bad files to an error folder. Design it.

Foreach Loop Container (File enumerator on the inbound folder, `*.csv`, map the file name to a variable). Inside: Flat File connection manager with its ConnectionString set by an expression from the variable; Data Flow (Flat File Source → Data Conversion/validation → error output to an error table → OLE DB Destination fast-load to staging); Execute SQL to merge staging into targets and log the file name/BatchId; File System Task on Success moves the file to Archive (with timestamp), on Failure moves it to Error. Event handler for alerts. Set `DelayValidation=True` because the file doesn't exist at design validation time.

## [Scenario|Medium] The same package must run against DEV, QA and PROD servers with different connection strings and file paths. How do you configure it?

Use the project deployment model: create project parameters (ServerName, DatabaseName, InboundFolder) and use them in connection manager expressions; deploy the same .ispac to each server's SSISDB; create an environment per server with variables holding the values (mark passwords as sensitive); reference the environment from the project and map parameters; SQL Agent job steps choose the environment. No package edits between environments.

## [Scenario|Medium] Your Lookup returns "No Match" for values that clearly exist in the reference table. Why?

Full-cache Lookup comparisons are **case-sensitive, accent-sensitive and type/whitespace-sensitive** (done in SSIS memory, not with the SQL collation). Differences in case, trailing spaces, data type (DT_STR vs DT_WSTR, int vs bigint) or code page cause misses. Fix: UPPER/TRIM both sides (in the reference query and a Derived Column), convert to identical types, or use partial/no cache so SQL's collation applies.

# Cheatsheet

## Building blocks

Package (.dtsx) · Project (.ispac) · Control Flow (tasks, containers, precedence constraints) · Data Flow (sources, transformations, destinations) · Connection managers · Variables · Parameters · Event handlers · Log/SSISDB.

## Key tasks

Execute SQL · Data Flow · Execute Package · File System · FTP · Script · Send Mail · Expression · Bulk Insert · CDC Control.

## Transformations by blocking type

- Non-blocking: Derived Column, Data Conversion, Conditional Split, Lookup, Multicast, Row Count, Copy Column, Audit.
- Semi-blocking: Merge, Merge Join, Union All, Pivot/Unpivot.
- Fully blocking: **Sort, Aggregate**, Fuzzy Lookup/Grouping.

## Lookup cache

Full (default, fastest) · Partial · No cache · Cache Connection Manager. Case/space/type sensitive.

## Error handling

Error output: Fail / Ignore / **Redirect row** · OnError event handler · MaximumErrorCount · Propagate=False · checkpoints · audit table.

## Deployment

Project model → SSISDB → folder → environments (DEV/QA/PROD) → parameter mapping → SQL Agent job → reports. `dtexec /ISServer ... /Env n /Par ...`.

## Performance

SQL source with filters · no Sort/Aggregate on big data · no OLE DB Command · full-cache lookups · fast load + table lock · buffer tuning · parallel tasks · staging + MERGE · incremental.
