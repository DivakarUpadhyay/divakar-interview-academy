# Overview

**Git** is a distributed version control system: every developer has the full history locally, commits offline, and synchronises with a shared **remote** (GitHub, Azure Repos, GitLab, Bitbucket).

| Term | Meaning |
|---|---|
| Repository (repo) | The project folder plus its full history (`.git` directory) |
| Commit | A snapshot of the project with author, message and parent commit(s) |
| Branch | A movable pointer to a commit |
| HEAD | Pointer to what you have checked out (usually a branch) |
| Working tree / staging area (index) / repository | Edited files → `git add` → `git commit` |
| Remote | Another copy of the repo, usually `origin` |
| Pull request (PR) / merge request | A request to merge a branch, with review and CI checks |

Git vs older tools: TFVC and SVN are **centralised** (one server holds history, you check out files); Git is **distributed**, branching is cheap and merging is fast.

# Lifecycle

**File states:** untracked → (`git add`) → staged → (`git commit`) → committed → (edit) → modified → staged again …

**Typical feature workflow:**

1. `git switch main && git pull` — start from the latest main.
2. `git switch -c feature/ORD-123-order-search` — create a branch.
3. Edit, `git add -p`, `git commit -m "Add order search endpoint"` — small, focused commits.
4. `git push -u origin feature/ORD-123-order-search`.
5. Open a **pull request**; CI runs build + tests; reviewers comment; you push fixes.
6. Update with main if needed (`git pull --rebase origin main` or merge main in).
7. Merge (merge commit, squash or rebase-merge per team policy); delete the branch.
8. Release: tag (`v2.3.0`) and deploy through CD.

# Module: Git Basics

## Lesson: [Basic|High] Setup, init, clone and the three areas

```bash
git config --global user.name "Divakar Upadhyay"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

git init                       # new repo in the current folder
git clone https://github.com/org/repo.git   # copy an existing repo (all history)
```

**The three areas:**

```text
Working tree  --git add-->  Staging area (index)  --git commit-->  Repository (.git)
   (your files)               (what goes in the next commit)          (history)
```

```bash
git status                     # what changed, what is staged
git add Program.cs             # stage one file
git add -p                     # stage chosen hunks interactively (great for clean commits)
git commit -m "Validate order quantity"
git log --oneline --graph --decorate --all
git diff                       # working tree vs staged
git diff --staged              # staged vs last commit
```

**`.gitignore`** — never commit build output, secrets or local settings:

```text
bin/
obj/
node_modules/
*.user
.vs/
appsettings.Development.json
.env
```

> **Interview tip:** A good commit message: short imperative summary (≤ 50 chars), blank line, then why. "Fix null reference when customer has no address".

## Lesson: [Basic|High] Branches, switching and merging

A branch is just a pointer to a commit — creating one is instant.

```bash
git branch                     # list local branches
git switch -c feature/login    # create and switch (older: git checkout -b)
git switch main                # go back
git merge feature/login        # merge into the current branch
git branch -d feature/login    # delete merged branch
```

**Fast-forward vs three-way merge:**

```text
Fast-forward (main has no new commits):     main ──A──B            feature: C──D
                                             result: main moves to D, no merge commit

Three-way (both moved):  main: A──B──E        feature: A──B──C──D
                         result: new merge commit M with parents E and D
```

`git merge --no-ff feature` forces a merge commit even when fast-forward is possible (keeps the feature grouped in history).

## Lesson: [Basic|High] Remotes — fetch, pull, push

```bash
git remote -v                          # list remotes
git fetch origin                       # download new commits, do NOT change your branch
git pull                               # fetch + merge (or rebase if pull.rebase=true)
git pull --rebase                      # fetch + replay your local commits on top
git push -u origin feature/login       # first push, set upstream
git push                               # later pushes
git push --force-with-lease            # safe force-push after rebase (fails if someone else pushed)
```

| Command | Changes your working branch? |
|---|---|
| `git fetch` | No — updates `origin/*` remote-tracking branches only |
| `git pull` | Yes — fetch then merge/rebase into your branch |

> **Interview tip:** "fetch is safe, pull integrates" — and never use plain `--force` on a shared branch; use `--force-with-lease`.

# Module: Working in a Team

## Lesson: [Intermediate|High] Merge conflicts — why they happen and how to resolve them

A conflict happens when two branches change the **same lines** (or one edits a file the other deleted) and Git can't decide.

```text
<<<<<<< HEAD
decimal discount = 0.10m;
=======
decimal discount = GetDiscount(customer);
>>>>>>> feature/discounts
```

Steps:

1. `git status` — lists conflicted files.
2. Edit each file: keep one side, both, or write a new combination; remove the markers.
3. Build and run tests.
4. `git add <file>` then `git commit` (merge) or `git rebase --continue` (rebase).
5. Changed your mind: `git merge --abort` / `git rebase --abort`.

Reduce conflicts: small PRs, merge main into long branches often, agree formatting (`.editorconfig`, Prettier), avoid giant files everyone edits.

## Lesson: [Intermediate|High] Rebase vs merge, squash and interactive rebase

```text
Before:   main: A──B──E          feature: A──B──C──D
Merge:    A──B──E──M (M joins E and D) — true history, extra merge commit
Rebase:   A──B──E──C'──D'        — feature replayed on top of E, linear history, new commit ids
```

```bash
git switch feature/search
git rebase main                 # replay my commits on top of main
git rebase -i HEAD~4            # interactive: squash, reword, reorder, drop commits
```

Interactive rebase todo list:

```text
pick 1a2b3c Add search endpoint
squash 4d5e6f Fix typo
squash 7a8b9c Address review comments
reword 0c1d2e Add search UI
```

**Golden rule:** never rebase commits that others have already pulled (shared/public branches) — rebase rewrites commit ids.

**PR merge options (GitHub/Azure Repos):** merge commit, **squash merge** (whole PR becomes one commit on main — popular), rebase and merge (linear, keeps individual commits).

## Lesson: [Intermediate|High] Pull requests, code review and branch policies

A good PR: one purpose, small (< ~400 changed lines), descriptive title, linked work item, screenshots for UI, tests included.

Branch protection / policies on `main`:

- Require PR (no direct pushes), at least 1–2 reviewers, code owners for sensitive folders.
- Require CI build + tests to pass (status checks).
- Require linked work item and resolved comments (Azure Repos).
- Require up-to-date branch / linear history; block force pushes.

Review checklist: correctness, tests, naming, security (secrets, SQL injection), performance, error handling, readability — comment on code, not on people.

## Lesson: [Intermediate|Medium] Branching strategies — GitFlow, GitHub Flow, trunk-based

| Strategy | Branches | Fits |
|---|---|---|
| **GitFlow** | `main` (releases), `develop`, `feature/*`, `release/*`, `hotfix/*` | Scheduled versioned releases (installed software, mobile) |
| **GitHub Flow** | `main` + short-lived feature branches, deploy after merge | Web apps with continuous delivery |
| **Trunk-based** | Everyone merges to `main` at least daily; feature flags hide unfinished work; release branches optional | High-performing CI/CD teams (DORA research) |
| **Release branches** | `main` + `release/2026.10` cut for stabilisation | Enterprise apps with UAT cycles |

Hotfix in GitFlow: branch from `main` → fix → merge to `main` (tag) **and** `develop`.

# Module: Undo, Inspect and Advanced Git

## Lesson: [Intermediate|High] Undoing things — restore, reset, revert, reflog

| Situation | Command |
|---|---|
| Discard changes in a file | `git restore Program.cs` |
| Unstage a file | `git restore --staged Program.cs` |
| Fix the last commit message / add a forgotten file (not pushed) | `git commit --amend` |
| Undo last commit, keep changes staged | `git reset --soft HEAD~1` |
| Undo last commit, keep changes unstaged | `git reset HEAD~1` (mixed, default) |
| Throw away last commit and changes | `git reset --hard HEAD~1` (dangerous) |
| Undo a commit that is already pushed/shared | `git revert <sha>` — new commit that reverses it |
| "I lost a commit / branch" | `git reflog` → find the sha → `git switch -c rescue <sha>` |
| Put work aside | `git stash push -m "wip"` → `git stash list` → `git stash pop` |

**reset vs revert:** `reset` moves the branch pointer (rewrites history — only for local commits); `revert` adds a new commit (safe for shared history).

## Lesson: [Advanced|Medium] Cherry-pick, bisect, tags, blame and hooks

```bash
git cherry-pick 4d5e6f          # copy one commit onto the current branch (e.g. a hotfix into release)
git tag -a v2.3.0 -m "Release 2.3.0" && git push origin v2.3.0   # annotated tag for a release
git blame -L 40,60 OrderService.cs   # who changed these lines and in which commit
git log -S "CalculateDiscount" --oneline   # commits that added/removed this text
git bisect start; git bisect bad; git bisect good v2.2.0   # binary-search the commit that introduced a bug
git bisect run dotnet test      # let tests decide good/bad automatically
git bisect reset
```

**Hooks** — scripts in `.git/hooks` (or managed by Husky / pre-commit): `pre-commit` (format, lint, block secrets), `commit-msg` (enforce message format), `pre-push` (run tests). Server-side checks belong in CI and branch policies, because local hooks can be skipped.

**Big repos:** Git LFS for large binaries, shallow clone (`--depth 1`) in CI, sparse-checkout for monorepos, `git worktree` to have two branches checked out at once.

## Lesson: [Advanced|Medium] How Git stores data — objects, SHA and refs

Git is a **content-addressed** store. Everything is an object named by its hash:

| Object | Holds |
|---|---|
| blob | File contents |
| tree | A directory: names → blobs/trees |
| commit | Root tree + parent commit(s) + author + message |
| tag (annotated) | Points to a commit with tagger and message |

Branches and tags are **refs** — small files containing a commit id (`.git/refs/heads/main`). `HEAD` usually contains `ref: refs/heads/main`. "Detached HEAD" means HEAD points directly at a commit, not a branch — commits made there are easy to lose unless you create a branch.

Because each commit includes its parent's id, changing any old commit changes every id after it — that's why rebase and amend create **new** commits and why rewriting shared history hurts teammates.

# Interview

## [Beginner|High] What is Git and how is it different from SVN/TFVC?

Git is a distributed version control system: every clone has the full history, so commits, branches, diffs and logs work offline and are fast; you sync with remotes by push/pull. SVN and TFVC are centralised: history lives on one server, many operations need the server, and branching is heavier. Git's cheap branching enables feature branches and pull-request workflows.

## [Beginner|High] What is the difference between git fetch and git pull?

`git fetch` downloads new commits and updates remote-tracking branches (`origin/main`) without touching your working branch — safe to run anytime. `git pull` = fetch + integrate (merge by default, or rebase with `--rebase`/`pull.rebase=true`) into your current branch, which can cause conflicts.

## [Beginner|High] What is the staging area?

The index between your working tree and the repository. `git add` puts selected changes into it and `git commit` records exactly what is staged. It lets you build clean, focused commits from a messy working tree (`git add -p` to stage parts of a file).

## [Beginner|High] How do you resolve a merge conflict?

Run `git status` to see conflicted files, open each, decide the correct code between the `<<<<<<<`, `=======`, `>>>>>>>` markers (keep one side, both, or rewrite), remove the markers, build and test, then `git add` the files and `git commit` (or `git rebase --continue`). Use `git merge --abort` to back out. Prevent conflicts with small, frequent merges.

## [Beginner|Medium] What does .gitignore do? A file is still tracked after adding it to .gitignore — why?

`.gitignore` stops **untracked** files from being added (bin/obj, node_modules, secrets). It doesn't affect files already tracked; remove them from the index with `git rm --cached <file>` and commit, and they will be ignored from then on (if it was a secret, rotate it — it is still in history).

## [Intermediate|High] Merge vs rebase — differences and when to use each?

Merge joins histories with a merge commit, keeps the true history and never rewrites commits — safe for shared branches. Rebase replays your commits on top of another branch, giving a linear history but new commit ids — use it for local/private branches to update with main or clean up before a PR. Never rebase commits others already have.

## [Intermediate|High] git reset vs git revert?

`reset` moves the current branch pointer back (soft keeps changes staged, mixed keeps them unstaged, hard discards them) — it rewrites history, so only for unpushed commits. `revert` creates a new commit that undoes a previous commit — the safe way to undo something already pushed to a shared branch.

## [Intermediate|High] Which branching strategy have you used? Explain it.

Describe yours concretely, e.g. "GitFlow-like: `main` = production, `develop` for integration, `feature/*` per story with PRs into develop, `release/*` cut for UAT, `hotfix/*` from main merged back to both" — or "trunk-based: short-lived branches merged to main daily behind feature flags, every merge deploys to dev". Mention branch policies (reviewers, CI checks) and how releases are tagged.

## [Intermediate|High] What is a pull request and what do you check in a code review?

A request to merge a branch, where teammates review the diff and CI validates it before merge. Check: does it meet the requirement, tests, edge cases and error handling, security (secrets, injection, authorization), performance (N+1, missing indexes), naming and readability, consistency with architecture, and that the PR is small and focused.

## [Intermediate|Medium] What is git stash?

Temporarily shelves uncommitted changes so you can switch context: `git stash push -m "msg"` (add `-u` for untracked files), `git stash list`, `git stash pop` (apply and drop) or `git stash apply` (keep in stash). Useful when an urgent bug arrives mid-feature.

## [Intermediate|Medium] What is cherry-pick and when would you use it?

`git cherry-pick <sha>` applies the changes of one commit onto the current branch as a new commit. Typical use: bring a hotfix from main into a release branch, or rescue a commit made on the wrong branch. Overuse creates duplicate commits — prefer merging when you need a whole branch.

## [Advanced|Medium] What is a detached HEAD?

HEAD points directly to a commit instead of a branch — after checking out a tag or a commit sha. You can look around and even commit, but new commits belong to no branch and can be garbage-collected once you switch away. Create a branch (`git switch -c fix-from-tag`) to keep them.

## [Advanced|Medium] How does git bisect help find a bug?

It binary-searches history between a known good and a known bad commit: Git checks out the midpoint, you mark it good or bad (or `git bisect run <test script>` does it automatically), and in log2(n) steps it names the first bad commit. Great for regressions in long histories.

## [Advanced|Medium] How does Git store data internally?

As content-addressed objects (blob = file content, tree = directory, commit = tree + parents + metadata, annotated tag) named by their SHA-1 (SHA-256 optional) hash, compressed in `.git/objects` and packfiles. Branches/tags are refs pointing at commit ids; HEAD points at a ref. Changing any commit changes its hash and all descendants' hashes.

## [Scenario|High] You committed a password and pushed it to GitHub. What do you do?

First **rotate/revoke the secret immediately** — assume it is compromised (bots scan GitHub within minutes). Then remove it from the code (move to Key Vault/user secrets/environment variables), and purge it from history with `git filter-repo` or BFG, force-push and ask everyone to re-clone; on GitHub contact support to clear cached views. Prevent it next time: `.gitignore`, pre-commit secret scanning (gitleaks), GitHub push protection / secret scanning.

## [Scenario|High] You made three commits on main by mistake instead of a feature branch (not pushed). Fix it.

`git branch feature/x` (new branch points at your commits) → `git reset --hard origin/main` (move main back to the remote state) → `git switch feature/x` and continue. Nothing is lost; if anything goes wrong, `git reflog` shows the old position.

## [Scenario|High] A bad commit is already deployed from main. How do you undo it without rewriting history?

`git revert <sha>` (for a merge commit `git revert -m 1 <merge-sha>`), push through the normal PR/pipeline so the revert is reviewed and deployed. Don't `reset` + force-push a shared branch — it breaks everyone's clones and the audit trail.

## [Scenario|Medium] Your feature branch is two weeks behind main and has many conflicts. How do you bring it up to date?

Fetch first. If the branch is only yours: `git rebase origin/main`, resolve conflicts commit by commit (`git rebase --continue`), run tests, `git push --force-with-lease`. If shared: `git merge origin/main` once and resolve in one merge commit. Afterwards keep it short-lived and sync daily; consider splitting the work into smaller PRs behind a feature flag.

## [Scenario|Medium] git push is rejected with "non-fast-forward". What does it mean?

The remote branch has commits you don't have, so pushing would overwrite them. `git pull --rebase` (or `git pull`), resolve any conflicts, test, then push. Only force-push (`--force-with-lease`) when you intentionally rewrote your own branch.

## Daily commands

```bash
git status | git add -p | git commit -m "msg" | git push
git switch -c feature/x | git switch main | git pull --rebase
git log --oneline --graph --all | git diff --staged
```

## Undo table

| Need | Command |
|---|---|
| Discard file edits | `git restore f` |
| Unstage | `git restore --staged f` |
| Edit last local commit | `git commit --amend` |
| Undo local commits | `git reset --soft/--mixed/--hard HEAD~n` |
| Undo pushed commit | `git revert sha` |
| Find lost work | `git reflog` |

## Merge vs rebase

Merge = true history, safe for shared branches. Rebase = linear history, rewrites ids — only on your own branches. Squash merge = one commit per PR on main.

## Branching strategies

GitFlow (develop/release/hotfix, versioned releases) · GitHub Flow (main + short branches) · Trunk-based (daily merges + feature flags).

## Safety rules

Never commit secrets (rotate if you do) · `--force-with-lease`, never `--force` on shared branches · protect `main` with PR + CI policies · small PRs, frequent syncs · tag every release.
