# Overview

**ETL** = **Extract** data from sources, **Transform** it (clean, validate, conform, aggregate), **Load** it into a target — usually a **data warehouse** used for reporting and analytics.

**ELT** = Extract, Load raw data first into a powerful target (cloud warehouse/lakehouse), then Transform inside it with SQL (dbt, Spark, Fabric). Modern cloud platforms favour ELT.

| | ETL | ELT |
|---|---|---|
| Transform where | Separate engine (SSIS, Informatica) | Inside the target (Synapse, Fabric, Snowflake, Databricks) |
| Raw data kept | Often not | Yes (data lake "bronze" layer) |
| Scale | Limited by ETL server | Elastic cloud compute |
| Typical tools | SSIS, Informatica PowerCenter, Talend, DataStage | Azure Data Factory/Fabric pipelines + dbt/Spark, Databricks, Snowflake |

**OLTP vs OLAP:** OLTP systems (orders, banking) handle many small transactions, normalised; OLAP systems (warehouses) handle large analytical queries, denormalised star schemas, historical data.

# Lifecycle

**ETL process lifecycle:**

1. **Requirements** — business questions, KPIs, sources, refresh frequency (SLA), history needs.
2. **Source analysis / profiling** — volumes, keys, data quality, how changes can be detected.
3. **Design** — target model (star schema), staging area, mappings (source-to-target document), load strategy (full/incremental), SCD types, error handling.
4. **Build** — packages/pipelines, transformations, lookups, logging.
5. **Test** — row counts, reconciliation with source, data quality checks, performance, rerun/idempotency.
6. **Deploy** — dev → test → prod (SSIS catalog, ADF CI/CD), with environment-specific parameters.
7. **Schedule & orchestrate** — SQL Agent, ADF triggers, Airflow; dependencies between jobs.
8. **Monitor & support** — alerts on failure, SLA tracking, audit tables, reprocessing failed batches.
9. **Maintain** — schema changes in sources, performance tuning, archiving.

**Data flow per run:** Source → **Extract** (full or delta) → **Staging** (raw copy, truncated each run) → **Transform** (cleanse, standardise, deduplicate, lookup surrogate keys, apply business rules, SCD logic) → **Load** dimensions first → **Load facts** → **Audit/log** → **Reconcile**.

# Module: Fundamentals

## Lesson: [Basic|High] What ETL is and why it is needed

Operational systems store data for running the business; they are not designed for analysis:

- Data is spread across systems (ERP, CRM, Excel, APIs) with different formats and keys.
- Running heavy reports on OLTP databases slows down the business.
- History is overwritten in OLTP (customer moves city — old city lost).

ETL creates a **single, clean, integrated, historical** copy optimised for analysis.

```
[ERP SQL Server] ─┐
[CRM API]        ─┼─ Extract ─► Staging ─► Transform ─► Data Warehouse (star schema) ─► Power BI / SSRS
[Excel / CSV]    ─┘                                          ▲
                                               logs, audit, error tables
```

## Lesson: [Basic|High] Full load vs incremental (delta) load

| | Full load | Incremental load |
|---|---|---|
| What | Reload everything each run | Only new/changed rows since last run |
| Simple? | Very | Needs change detection |
| Volume/time | Grows with data | Small and fast |
| Deletes | Handled naturally (truncate + load) | Must be detected separately |
| Use | Small tables, initial load, dimensions with no change tracking | Large/fast-growing tables |

Change detection techniques:

1. **Watermark column** — `ModifiedDate > @LastLoadTime` (store the high-water mark in a control table).
2. **Rowversion/timestamp** column.
3. **Change Data Capture (CDC)** — SQL Server reads the transaction log into change tables (inserts/updates/deletes with before/after values).
4. **Change Tracking** — lightweight: which rows changed (not the values).
5. **Hash comparison** — compare a hash (e.g. `HASHBYTES('SHA2_256', ...)`) of columns between source and target.
6. **Triggers** writing to audit tables (adds OLTP overhead).

```sql
-- Watermark pattern
DECLARE @Last DATETIME2 = (SELECT LastLoaded FROM etl.Watermark WHERE TableName = 'Orders');
DECLARE @Now  DATETIME2 = SYSUTCDATETIME();

INSERT INTO stg.Orders SELECT * FROM src.Orders WHERE ModifiedAt > @Last AND ModifiedAt <= @Now;
-- transform + load ...
UPDATE etl.Watermark SET LastLoaded = @Now WHERE TableName = 'Orders';   -- only after success
```

## Lesson: [Basic|High] Staging area and the medallion architecture

**Staging** = a landing zone holding raw extracted data, usually truncated and reloaded each run. Benefits: decouples extraction from transformation, reduces load on sources (extract once), allows reprocessing, simplifies debugging and reconciliation.

**Medallion architecture** (lakehouse):

| Layer | Content |
|---|---|
| **Bronze** | Raw data as ingested (append-only, full history) |
| **Silver** | Cleaned, deduplicated, conformed, validated |
| **Gold** | Business-level aggregates and star schemas for reporting |

## Lesson: [Basic|Medium] Common transformations

- **Cleansing** — trim, fix case, standardise formats (dates, phone numbers), handle NULLs/defaults.
- **Validation** — reject or flag rows breaking rules (missing keys, invalid dates).
- **Deduplication** — `ROW_NUMBER() OVER (PARTITION BY businessKey ORDER BY ModifiedAt DESC)`.
- **Lookups** — map business keys to **surrogate keys** of dimensions.
- **Derivations** — calculated columns (Margin = Revenue − Cost).
- **Data type conversion** — string → date/decimal (with error handling).
- **Aggregation**, **pivot/unpivot**, **split/merge** columns, **joins/merges** across sources.
- **Conforming** — same meaning and codes across sources (e.g. Gender 'M'/'Male'/1 → 'M').

# Module: Dimensional Modelling

## Lesson: [Intermediate|High] Facts, dimensions, star and snowflake schemas

- **Fact table** — numeric, measurable events (sales amount, quantity) at a defined **grain**, with foreign keys to dimensions. Usually long and narrow.
- **Dimension table** — descriptive context (who, what, where, when): Customer, Product, Date, Store. Wide, with attributes for filtering and grouping.
- **Star schema** — fact in the middle, denormalised dimensions around it (one join per dimension) → simple and fast.
- **Snowflake schema** — dimensions normalised into sub-dimensions (Product → Subcategory → Category) → less redundancy, more joins.
- **Galaxy / fact constellation** — multiple facts sharing **conformed dimensions** (e.g. DimDate, DimCustomer used by FactSales and FactReturns).

```sql
CREATE TABLE dw.DimDate (DateKey INT PRIMARY KEY, FullDate DATE, [Month] TINYINT, MonthName VARCHAR(10), [Quarter] TINYINT, [Year] SMALLINT, IsWeekend BIT);
CREATE TABLE dw.DimProduct (ProductKey INT IDENTITY PRIMARY KEY, ProductId VARCHAR(20), Name NVARCHAR(100), Category NVARCHAR(50));
CREATE TABLE dw.DimCustomer (CustomerKey INT IDENTITY PRIMARY KEY, CustomerId VARCHAR(20), Name NVARCHAR(100), City NVARCHAR(50),
                             ValidFrom DATE, ValidTo DATE, IsCurrent BIT);
CREATE TABLE dw.FactSales (
    DateKey INT REFERENCES dw.DimDate, ProductKey INT REFERENCES dw.DimProduct, CustomerKey INT REFERENCES dw.DimCustomer,
    OrderNumber VARCHAR(20),          -- degenerate dimension
    Quantity INT, SalesAmount DECIMAL(18,2), CostAmount DECIMAL(18,2));
```

## Lesson: [Intermediate|High] Types of facts and dimensions

**Fact types:**

| Type | Grain | Example |
|---|---|---|
| Transaction | One row per event | Each sale line |
| Periodic snapshot | One row per entity per period | Daily account balance, month-end inventory |
| Accumulating snapshot | One row per process instance, updated as milestones happen | Order: ordered → shipped → delivered dates |
| Factless | Events with no measures | Student attendance, promotion coverage |

**Measures:** additive (sum across all dimensions: amount), semi-additive (not across time: balance, inventory), non-additive (ratios, percentages — store components instead).

**Dimension types:** conformed (shared), role-playing (DimDate as OrderDate/ShipDate), junk (low-cardinality flags combined), degenerate (order number stored in the fact), slowly changing (see next lesson), outrigger (dimension referencing another).

**Surrogate key** — meaningless integer key generated in the warehouse; isolates from source key changes, enables SCD Type 2 history, makes joins faster. **Natural/business key** — the source system's ID, kept as an attribute.

## Lesson: [Intermediate|High] Slowly Changing Dimensions (SCD)

| Type | Behaviour | Example |
|---|---|---|
| **Type 0** | Never changes (retain original) | Date of birth |
| **Type 1** | **Overwrite** — no history | Fix a spelling mistake |
| **Type 2** | **New row** per change with ValidFrom/ValidTo/IsCurrent — full history | Customer moves city; past sales stay with old city |
| **Type 3** | **Extra column** for previous value — limited history | CurrentRegion, PreviousRegion |
| Type 4 | History in a separate table | Mini-dimension for rapidly changing attributes |
| Type 6 | 1 + 2 + 3 hybrid | Current value on every historical row + full history |

```sql
-- SCD Type 2 with T-SQL (expire changed rows, then insert new versions)
UPDATE d SET d.ValidTo = CAST(GETDATE() AS DATE), d.IsCurrent = 0
FROM dw.DimCustomer d
JOIN stg.Customer s ON s.CustomerId = d.CustomerId
WHERE d.IsCurrent = 1 AND (d.City <> s.City OR d.Name <> s.Name);

INSERT INTO dw.DimCustomer (CustomerId, Name, City, ValidFrom, ValidTo, IsCurrent)
SELECT s.CustomerId, s.Name, s.City, CAST(GETDATE() AS DATE), '9999-12-31', 1
FROM stg.Customer s
LEFT JOIN dw.DimCustomer d ON d.CustomerId = s.CustomerId AND d.IsCurrent = 1
WHERE d.CustomerKey IS NULL;      -- new customers + customers whose current row was just expired
```

Fact loads must look up the surrogate key **valid at the transaction date** (or the current row for new facts).

## Lesson: [Intermediate|Medium] Inmon vs Kimball, data marts, data lakes and lakehouses

- **Inmon (top-down)** — build a normalised enterprise data warehouse (3NF) first, then dependent data marts.
- **Kimball (bottom-up)** — build dimensional data marts per business process with conformed dimensions (the "bus matrix") — together they form the warehouse.
- **Data mart** — subject-specific subset (Sales mart, Finance mart).
- **Data lake** — cheap storage of raw data in any format (files: Parquet, CSV, JSON) — schema-on-read.
- **Lakehouse** — data lake + warehouse features (ACID tables via Delta/Iceberg, SQL, governance) — e.g. Databricks, Microsoft Fabric OneLake.
- **Data Vault 2.0** — hubs (business keys), links (relationships), satellites (attributes with history); agile, auditable raw warehouse layer.

# Module: Building Reliable Pipelines

## Lesson: [Intermediate|High] Error handling, logging, auditing and restartability

- **Audit table** per run: BatchId, Package/Pipeline, StartTime, EndTime, Status, RowsExtracted, RowsInserted, RowsUpdated, RowsRejected, ErrorMessage.
- **Error rows** redirected to error tables with the reason (instead of failing the whole load).
- **Idempotency** — rerunning the same batch gives the same result (truncate-and-reload staging; MERGE/upsert; delete batch by BatchId before reload).
- **Restartability / checkpoints** — resume from the failed step (SSIS checkpoints, ADF rerun from failed activity).
- **Transactions** — wrap dimension/fact loads so partial loads don't remain, or use batch-level delete-and-reload.
- **Alerts** — email/Teams on failure; SLA monitoring.
- **Reconciliation** — compare row counts and sums (e.g. total sales) between source and target.

## Lesson: [Intermediate|High] Data quality

Dimensions of data quality: **accuracy, completeness, consistency, timeliness, validity, uniqueness**.

Checks to automate:

- Not-null and allowed-value checks on key columns.
- Referential integrity: every fact has a matching dimension member (use an "Unknown" member, key −1, for late or missing dimensions — **late-arriving dimensions**).
- Duplicate business keys.
- Range checks (no negative quantities, dates not in the future).
- Row count / total amount reconciliation against the source.
- Freshness (data loaded within SLA).

```sql
-- Unknown member pattern
INSERT INTO dw.DimCustomer (CustomerKey, CustomerId, Name, City, ValidFrom, ValidTo, IsCurrent)
VALUES (-1, 'UNKNOWN', 'Unknown', 'Unknown', '1900-01-01', '9999-12-31', 1);   -- with IDENTITY_INSERT ON
```

## Lesson: [Advanced|Medium] Performance of large loads

- Extract only needed columns and only changed rows (incremental/CDC).
- Bulk load (SSIS fast load, `SqlBulkCopy`, `BULK INSERT`, PolyBase/COPY INTO in cloud warehouses) with batch sizes and `TABLOCK` for minimal logging.
- Drop/disable non-clustered indexes before huge loads and rebuild after (or load into an empty partition and switch in).
- Set-based SQL instead of row-by-row (avoid cursors, OLE DB Command per row).
- Parallelism — load independent tables concurrently.
- Partitioning of large facts (by date) for fast loads/archival.
- Push transformations to where data lives (ELT) when the target is powerful.
- Avoid blocking transformations (sort, aggregate) on huge flows in SSIS; sort in the source query instead.

## Lesson: [Intermediate|Medium] Orchestration and scheduling

- **SQL Server Agent** — schedules SSIS packages/T-SQL jobs on-prem, with steps, retries and notifications.
- **Azure Data Factory / Fabric pipelines** — triggers (schedule, tumbling window, storage event), activities (Copy, Data Flow, Stored Procedure, Notebook), dependencies, parameters, integration runtimes (Azure, self-hosted for on-prem sources, Azure-SSIS IR to run SSIS packages in the cloud).
- **Apache Airflow** — DAGs in Python.
- Design for dependencies (dimensions before facts), retries with backoff, timeouts, and alerting.

# Interview

## [Beginner|High] What is ETL? Explain each step.

ETL is the process of moving data from source systems into a target (usually a data warehouse). **Extract**: read data from databases, files, APIs — full or incremental. **Transform**: cleanse, validate, standardise, deduplicate, look up surrogate keys, apply business rules, aggregate. **Load**: write into dimension and fact tables (inserts, updates, SCD handling), then log and reconcile. Goal: consistent, integrated, historical data for reporting.

## [Beginner|High] What is the difference between ETL and ELT?

ETL transforms data in a separate engine before loading (SSIS, Informatica), good when the target is limited or data must be cleaned before landing. ELT loads raw data into a scalable target first and transforms it there with SQL/Spark (Synapse, Fabric, Snowflake, Databricks + dbt), keeping raw history and using elastic compute. Modern cloud architectures mostly use ELT with a medallion design.

## [Beginner|High] What is a data warehouse? How is it different from an OLTP database?

A data warehouse is a subject-oriented, integrated, time-variant, non-volatile store of data for analysis (Inmon's definition). OLTP databases serve day-to-day transactions: many small reads/writes, normalised, current data. Warehouses serve analytical queries over large volumes: denormalised star schemas, history, bulk loads, read-optimised (columnstore). Running analytics on OLTP harms the business application.

## [Beginner|High] What are fact and dimension tables?

Fact tables store measurable business events (quantity, amount) at a defined grain plus foreign keys to dimensions. Dimension tables store descriptive attributes (customer name, city; product category; date parts) used to filter and group facts. Example: FactSales(DateKey, ProductKey, CustomerKey, Qty, Amount) with DimDate, DimProduct, DimCustomer.

## [Beginner|High] What is the difference between a star schema and a snowflake schema?

In a star schema, each dimension is a single denormalised table directly joined to the fact — fewer joins, faster and simpler for BI tools. In a snowflake schema, dimensions are normalised into multiple related tables (Product → Subcategory → Category) — less redundancy but more joins and complexity. Kimball recommends star schemas; Power BI performs best with them.

## [Beginner|Medium] What is a staging area and why use it?

A temporary storage layer where extracted raw data lands before transformation. It minimises the time and load on source systems, allows transformations and validations with SQL, supports reruns without re-extracting, helps debugging and reconciliation, and decouples source availability from the warehouse load schedule. Usually truncated and reloaded each run (or kept as bronze history in lakehouses).

## [Intermediate|High] Explain Slowly Changing Dimensions Types 1, 2 and 3.

They control how dimension attribute changes are stored. Type 1 overwrites the old value (no history — corrections). Type 2 inserts a new row with a new surrogate key and validity columns (ValidFrom, ValidTo, IsCurrent), preserving full history so old facts keep pointing to the old version. Type 3 adds a column for the previous value (only one level of history). Type 0 never changes; Type 6 combines 1, 2 and 3.

## [Intermediate|High] What is a surrogate key and why use it in a warehouse?

A system-generated integer key (IDENTITY/sequence) used as the dimension's primary key instead of the source's natural key. Reasons: integrates multiple sources with overlapping IDs, enables SCD Type 2 (several rows per business key), protects from source key changes/reuse, smaller and faster joins, supports special members like "Unknown" (-1).

## [Intermediate|High] How do you implement an incremental load?

Detect changes since the last successful run using a watermark (ModifiedDate/rowversion stored in a control table), CDC or Change Tracking, or hash comparison. Extract only those rows into staging, then upsert into the target (MERGE or UPDATE + INSERT; SCD logic for dimensions), handle deletes (soft-delete flags, CDC delete records, or periodic full compare), and update the watermark only after the load succeeds so failures don't skip data.

## [Intermediate|High] How do you handle errors and bad data in ETL?

Validate early; redirect bad rows to error tables with the reason instead of failing the whole batch (unless the threshold is exceeded); use an "Unknown" dimension member for missing lookups (late-arriving dimensions) and fix later; log every run in an audit table (counts, durations, status); send alerts; make loads idempotent and restartable; reconcile counts and totals with the source; keep raw data for reprocessing.

## [Intermediate|Medium] What is the grain of a fact table and why is it important?

The grain is what one row represents (one order line, one customer per day, one account per month-end). It must be declared before choosing dimensions and measures. Mixing grains causes double counting. The most atomic grain gives the most flexibility; aggregates can be built on top.

## [Intermediate|Medium] What are additive, semi-additive and non-additive measures?

Additive measures can be summed across all dimensions (sales amount, quantity). Semi-additive can be summed across some dimensions but not time (account balance, inventory level — use last/average over time). Non-additive can't be summed at all (ratios, percentages, unit price) — store numerator and denominator and calculate in the report.

## [Intermediate|Medium] What is CDC (Change Data Capture)?

A SQL Server feature (also in Azure SQL and other databases) that reads the transaction log asynchronously and records inserts, updates and deletes with column values into change tables (`cdc.<schema>_<table>_CT`), queried via `cdc.fn_cdc_get_all_changes_...` using LSN ranges. ETL reads only changes — including deletes — with low impact on the source. Change Tracking is lighter: it records which rows changed, not the values.

## [Advanced|Medium] Inmon vs Kimball — which approach would you choose?

Inmon builds a normalised enterprise DW first (top-down) — consistent, but long time-to-value. Kimball builds dimensional data marts per business process using conformed dimensions (bottom-up) — faster delivery and BI-friendly. Many organisations use a hybrid: a raw/normalised (or Data Vault) integration layer with Kimball star schemas for presentation — similar to the medallion bronze/silver/gold pattern.

## [Advanced|Medium] What is a late-arriving dimension (early-arriving fact) and how do you handle it?

A fact arrives referencing a dimension member that doesn't exist yet (e.g. sale for a new customer not yet loaded from CRM). Options: assign the "Unknown" member (-1) and update the fact later; or insert an **inferred member** (placeholder row with just the business key) and update its attributes when the real dimension data arrives (SSIS SCD wizard supports inferred members).

## [Scenario|High] The nightly ETL that used to take 1 hour now takes 5 hours and misses the SLA. How do you troubleshoot?

Find which step slowed (audit log durations per task). Check data volume growth (switch full loads to incremental), source query plans and missing indexes, blocking on target tables during loads, row-by-row operations (OLE DB Command, cursors, SCD wizard on big dimensions → replace with set-based MERGE), blocking SSIS transformations (sort/aggregate), lookups in full-cache mode with huge reference tables, index maintenance on targets (disable/rebuild), log growth, server resources (memory, tempdb), and parallelism between independent loads.

## [Scenario|High] Business reports show sales totals 3% higher than the ERP. How do you find the cause?

Reconcile step by step: compare counts and sums source → staging → warehouse for the same period and filters. Typical causes: duplicate extraction (overlapping incremental windows, reruns without idempotency), join fan-out (fact joined to a dimension with duplicate business keys, SCD2 lookup not restricted to the valid row), different business rules (cancelled orders, returns, tax/currency, time zones/cut-off), late-arriving corrections not applied. Fix the logic, add automated reconciliation checks and uniqueness tests.

## [Scenario|Medium] Design an ETL for daily sales from 50 store databases into a central warehouse.

Parameterised pipeline looped over a store config table (ADF ForEach or SSIS Foreach with a project parameter for the connection). Incremental extract per store using a watermark/CDC into a staging table tagged with StoreId and BatchId. Transform centrally: conform codes, dedupe, look up surrogate keys (DimStore, DimProduct, DimDate, DimCustomer with SCD2). Load dimensions then FactSales (partitioned by date). Audit table per store per run, error rows redirected, alerts for stores that failed, rerun only failed stores. Schedule after stores close; monitor SLA.

## [Scenario|Medium] How do you test an ETL pipeline?

Unit-test transformations (sample inputs → expected outputs), validate mappings against the source-to-target document, test row counts and sums (reconciliation), null/duplicate/RI checks, SCD behaviour (insert, change, no-change cases), incremental logic (no duplicates on rerun, late changes captured, deletes handled), error handling (bad rows go to error tables), performance with production-like volumes, and restart/idempotency. Automate with tSQLt, dbt tests or Great Expectations in CI.

# Cheatsheet

## ETL vs ELT

ETL: transform before load (SSIS). ELT: load raw, transform in the warehouse (ADF/Fabric + SQL/dbt/Spark).

## Load types

Full (truncate + reload) · Incremental (watermark, rowversion, CDC, Change Tracking, hash) · Upsert (MERGE) · Deletes (soft delete, CDC, full compare).

## Dimensional model

Fact (measures at a grain) + Dimensions (descriptive) · Star (denormalised) vs Snowflake (normalised dims) · Surrogate keys · Conformed, role-playing, junk, degenerate dimensions.

## Fact types

Transaction · Periodic snapshot · Accumulating snapshot · Factless. Measures: additive, semi-additive, non-additive.

## SCD

0 keep · **1 overwrite** · **2 new row + ValidFrom/ValidTo/IsCurrent** · 3 previous-value column · 4 history table · 6 hybrid.

## Reliability

Staging · audit table · error tables · Unknown member (-1) · idempotent reruns · watermark updated after success · reconciliation counts/sums · alerts.

## Architectures

Inmon (top-down 3NF) · Kimball (bottom-up stars) · Data Vault (hubs/links/satellites) · Data lake · Lakehouse · Medallion bronze → silver → gold.

## Tools

SSIS · ADF · Fabric · Synapse · Databricks · Informatica · Talend · Airflow · dbt · Spark · Kafka.
